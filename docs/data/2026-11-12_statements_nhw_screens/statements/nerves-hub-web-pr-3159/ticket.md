I need the workflow step transitions and halted-workflow notifications cleaned up so the orchestrator, dashboard, and Slack can act on the same step without one overwriting the other, and so a workflow halt is announced exactly once and the notifications page only hears about it after the change has been persisted.

The callable Workflows API should become:

- `Workflows.start_step/2`: `(deployment_group, step)` -> `{:ok, step}` when the step can move from waiting to in progress. If the step has already moved since the caller read it, return an error tuple and leave it alone; callers should treat that as nothing active this pass.
- `Workflows.complete_step/1`: `(step)` -> `{:ok, step}` when the current step is in progress, otherwise `{:error, :not_in_progress}`.
- `Workflows.fail_step/3`: `(deployment_group, step, failed_device_count)` -> `{:ok, step}` when the current step is in progress, otherwise `{:error, :not_in_progress}`.
- `Workflows.approve_step/4`: `(deployment_group, step, user, opts \\ [])` -> `{:ok, step}` only when the current step is an `approval_required` step that is in progress with no `approved_at`, otherwise `{:error, :not_approvable}`.
- `Workflows.skip_step/4`: `(deployment_group, step, user, opts \\ [])` -> `{:ok, step}` or `{:error, :not_skippable}`.
- `Workflows.retry_step/4`: `(deployment_group, step, user, opts \\ [])` -> `{:ok, step}` or `{:error, :not_retryable}`.

All successful transitions should return the updated current step and still announce the existing `step/updated` broadcast with its id, number, and new status. A caller holding a stale copy must never write that stale status back: for example, a step skipped during an orchestrator pass must not later be failed or completed from the stale copy, and retrying or approving twice must only work once.

For `approve_step`, `skip_step`, and `retry_step`, `:via` in `opts` is the human-readable place an action came from, for example `via: "Slack user U0ALICE"`. The audit entry for the action must be written by the Workflows operation itself, attributed to the user, with the existing action names `:approved`, `:skipped`, or `:retried`, and including the via text when present. For example, that skip should show both `User Alice skipped workflow step 1` and `from Slack user U0ALICE`. The dashboard and Slack call sites must not add their own duplicate audit entries.

All of the side effects of a successful status change need to stand or fall together: device claims released by skip/retry, workflow events, audit entry, and halt notification creation/resolution. If the audit or halt notification part fails, the step status and device claims must remain as they were and the operation should fail; a later orchestrator pass may try again. The notifications-page event is the exception: it must be emitted only after the whole change has succeeded, so the page reads back final state instead of an intermediate one.

Workflow halts:

- Starting an `approval_required` step is the moment its halt is raised: set in progress and `started_at`, announce `awaiting_approval`, write the existing “is waiting for approval” audit entry, create the product notification with the existing title beginning `A deployment workflow is waiting for approval.`, and emit the existing `[:nerves_hub, :deployments, :workflow, :halted]` telemetry event with `count: 1` and `reason: :awaiting_approval` plus the usual deployment/step metadata. This must happen when the step is started, whether from the orchestrator or directly, and must not be repeated by later passes that only observe the same waiting step.
- Starting a non-approval step still announces `started` and raises no halt.
- Failing a step is the moment its halt is raised: set error and `finished_at`, announce `failed` with the failure count, write the failed audit entry, create the corresponding notification, and emit the halted telemetry with `reason: :failed`. If creating that notification fails, the step must stay in progress; a later pass can fail it again.
- A workflow that remains halted must not be announced again on each orchestrator pass. Repeated passes observing the same waiting or failed step should leave the already-created notification coalesced, with `occurrence_count` staying at 1.
- The orchestrator should no longer separately create halt notifications, audits, or telemetry. It should call the step transitions above, log on success, and quietly stop the pass when a transition reports that the step moved since the pass read it. `WorkflowCoordinator.schedule_updates/1`’s existing return contract should stay.

Completing a step, approving, skipping, retrying, and the workflow events already used for Slack messages should keep their current behavior: `awaiting_approval`, `started`, `completed`, `failed`, `approved`, `skipped`, `retried`, and the Slack message resolution/update jobs still get the same actions and users. Approving or skipping an approval halt must resolve the outstanding product notification so it disappears from the list.

The halted-notification helpers need to support deferring their page event: `ProductNotifications.create_workflow_halted_notification!/4` should keep creating the same notification and return it, but accept an options argument that suppresses its immediate created event when the caller will emit it after the change is durable; `ProductNotifications.resolve_workflow_halted_notification!/4` should return `{:ok, :resolved}` when it removed a notice and `{:ok, :none}` when there was nothing to remove, with the same defer option suppressing its resolved event. A resolved event is emitted only when something was actually resolved. Existing callers that do not defer should keep the current default behavior.

The dashboard approval handler should handle the case where the step disappeared or is no longer approvable between render and click by clearing `awaiting_approval` and not crashing or showing an incorrect success flash. Successful approval still nudges the orchestrator and shows the existing success message. Skip/retry handlers should use the new signatures and rely on Workflows for auditing. Slack step actions should call these same functions with the via text, and on `:not_approvable`, `:not_skippable`, or `:not_retryable` show the existing friendly message rather than crashing; approving something already moved on should say it is no longer waiting for approval. All existing call sites that start, complete, fail, approve, skip, or retry a step need updating to the new signatures, including direct start calls used when previewing or visiting a deployment group.

Out of scope: workflow definition format, step schema fields, routes, UI layout, and changing notification or Slack copy beyond the above. Keep `release_steps/1`, the existing `step/updated` broadcasts, notification keys/copy, and the existing public workflow event behavior compatible.
