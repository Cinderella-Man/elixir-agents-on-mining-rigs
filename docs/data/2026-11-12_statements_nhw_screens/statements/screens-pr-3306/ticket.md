We’re extending the delayed/cancelled departure treatment from DUP to all v2 LCD apps (bus shelter, busway, DUP, pre-fare). The goal is that when a trip is delayed or cancelled, the screen can show the originally scheduled time on the normal page-rotation cycle instead of only doing so on DUP.

Behaviour to preserve and settle:
- Page rotation should become shared across all v2 screen apps, not just DUP. It should keep the DUP baseline: once the screen is onscreen, alternate pages every 3750 ms; if MRAID is unavailable, start rotating immediately.
- For departure rows, normal/near-term rows and DUP rows should take part in the scheduled/predicted alternation. Later departures should not alternate; they should always show the predicted/current time.
- On LCD, delayed departure times should be grey `#6e6e6e`; delayed and cancelled departure times should be struck through. The strike-through must carry through to the scheduled-time text shown on the alternate page, not only the outer container.
- Backend serialization: `Screens.V2.WidgetInstance.Departures.serialize_times_with_crowding/3` should no longer be screen-app specific. For every departure and every v2 screen, return one serialized time entry rather than dropping cancelled predictions that have a schedule. Keep the existing `id`, `crowding`, `time`, `scheduled_time`, `is_live`, and `time_in_epoch` fields. Include `scheduled_time` only when: a schedule exists; the predicted time is nil or a timestamp; and the serialized scheduled time differs from the serialized predicted time. If the predicted time is the same timestamp, omit `scheduled_time`. If the predicted time is text/counted-down/etc., omit `scheduled_time`. If there is no schedule, omit `scheduled_time`. A cancelled/skipped departure with no prediction time and a schedule should come back with `time: nil` and a timestamp `scheduled_time`, for both DUP and non-DUP screens.
- RDS: when assembling headways from multiple states, the same route can appear more than once. The `routes` in the RDS headways output should be deduplicated, preserving first-seen order.

Out of scope: changing which departures are produced/selected, adding new API routes, changing non-v2 screens, or changing the serialized shape beyond the extra scheduled-time cases and route deduplication. The existing DUP output and the existing fields in `serialize_times_with_crowding/3` must remain compatible.
