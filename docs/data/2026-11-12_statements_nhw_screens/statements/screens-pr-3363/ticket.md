The admin tools' image content cleanup should now cover wayfinding content as well as evergreen content. Keep the existing evergreen cleanup behavior and the existing POST /api/admin/maintenance action "image_content_cleanup"; that same action should now handle both content types. On the tools page, label the section Content Cleanup instead of Evergreen Content Cleanup, and make the scheduled-cleanup description and confirmation prompt refer to both evergreen and wayfinding content. The prompt should still include the number of affected screens. Leave the alert content cleanup behavior alone.

For wayfinding, look at each screen config's app_params.departures.sections. A section header has a wayfinding_information field, which can be a ScreensConfig.Departures.Header.WayfindingInformation with a schedule list. Treat wayfinding information as expired only when every schedule has a non-nil end_dt strictly earlier than the before date. If any schedule has a nil end_dt, or any schedule ends on or after the cutoff, leave that wayfinding information alone. If wayfinding_information is already nil, leave it alone. A screen without departures, without sections, or without wayfinding information is unchanged.

When an eligible wayfinding item is found, clear it by setting that section header's wayfinding_information to nil. Leave the rest of the section and screen config unchanged, and a screen with several eligible sections should still produce only one update for that screen. For example, with a before date of 2025-01-01, schedules ending 2024-10-03 and 2024-11-03 should be cleaned; a screen with one schedule ending 2024-10-03 and one ending 2025-02-03 should not be cleaned; a screen with one ending 2024-10-03 and one nil should not be cleaned.

Add a public Screens.Util.Admin.wayfinding_content_cleanup_updates/2 taking the list of screen configs and the Date.t() cutoff. It should return the same update shape as evergreen_content_cleanup_updates/2: a list of maps with :id and :config, only one entry per screen config whose resulting config changed, and no entry for unchanged configs. It should not replace or change the evergreen cleanup function. A screen config with expired wayfinding content in multiple sections counts as one affected screen.

For the controller, keep the existing image_content_cleanup request shape: action "image_content_cleanup", an ISO date in "before", and optional "dry_run" => "true". On a dry run, return %{"affected" => n} with no writes or cache invalidation. For this action, n is the number of evergreen cleanup updates plus the number of wayfinding cleanup updates; a screen that needs both kinds of cleanup contributes once for each kind. Without dry_run, apply both kinds of cleanup, commit the resulting screen config updates through the existing persistence path, keep the existing cache invalidation and error behavior, and return the same success response as before. If no content qualifies, the count is zero and no configs are changed.
