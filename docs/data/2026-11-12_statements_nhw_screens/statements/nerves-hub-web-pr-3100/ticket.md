We need TLS session resumption for the device endpoint. A device that reconnects should be able to present a ticket from an earlier full handshake and resume; the first connection must not be resumed and the server must issue at least one ticket. Resumption has to work both with and without the PROXY protocol. A resumed connection must still present the peer certificate, because the device connection is authenticated by certificate; do not use a resumption mode that drops the certificate. A resumed connection is still a new connection, so the peer address reported is from its own PROXY header, not from the earlier connection. If a ticket is no longer accepted, fall back to a full handshake.

With PROXY protocol enabled, the TLS listener must stay owned by `:ssl` and accept connections as TLS; do not accept in the clear and upgrade later, because that does not give resumable sessions. The PROXY header still has to be consumed before TLS reads application data, with the existing 5 second header timeout. Accepting must not wait for the header; a client that never sends one must not block the acceptor. A malformed or missing header is rejected. A LOCAL header that names no client reports the socket's own peer, as does a connection without PROXY. All transport options passed to the listener still apply; proxy mode must not discard TLS options such as the certificate, verify settings, versions, or the resumption option.

In production runtime config, the existing `DEVICE_ENABLE_TLS_13` switch should add session resumption alongside `certificate_authorities: false`, using the transport option `session_tickets: :stateless_with_cert`. Leave the branch that forces TLS 1.2 alone. If deployment supplies a shared resumption seed, use it across nodes so tickets survive restarts/deploys and any node can accept them; if it is absent, each node may use its own. Reject a shared seed shorter than 64 bytes at startup with a clear error. Changing the seed invalidates all existing tickets and devices simply do full handshakes. Keep the seed as sensitive as other signing secrets. Only ordinary resumption is in scope: no zero-round-trip application data or new early handshake paths.

The peer address from a PROXY header has to remain available after the socket closes, because a handler may ask for peername after the client has gone. Add `NervesHub.ProxyProtocol.Peers` as a supervised process started before the device endpoint, with a public, named ETS table also called `Peers`. Its API:

- `expect/1`: called for each accepted PROXY-mode port; records it as waiting for its header and monitors the port. If the port is already closed, it must still arrange forgetting.
- `put/2`: stores the peer tuple, for example `{{203, 0, 113, 7}, 51_234}`, for the socket. Store the raw peer tuple in ETS as `{socket, peer_tuple}` so direct ETS lookups see that tuple. A header that names no client is resolved to the socket's own peer while the socket is still open and stored the same way, so it can still be answered after hang-up. If no peer can be found, record that there is no address so `get/1` returns nil.
- `get/1`: returns that peer tuple, or nil if none is available. While the header is pending, `get/1` is nil.

The GenServer state must be a map with a `remember_for` field, default 60_000 milliseconds. When a monitored socket goes down, schedule a `{:forget, socket}` message after `remember_for`; on `{:forget, socket}`, delete the socket's ETS entry. Do not delete immediately on socket close. If `remember_for` is 0, the forgetting should happen promptly. This gives one entry per connection, cleaned up regardless of how the socket closed, and no unbounded growth. The address is per socket, not per certificate or session.

The transport behind PROXY must answer `peername/1` from that stored address and must keep answering after the socket has closed; a missing stored address falls back to the underlying socket's peer while it still exists. The header is consumed at most once per socket, and the existing handshake rate-limit gate stays before TLS processing. Other transport callbacks go to the SSL transport. The no-PROXY path continues to report the normal SSL peer and delegate all callbacks to SSL.
