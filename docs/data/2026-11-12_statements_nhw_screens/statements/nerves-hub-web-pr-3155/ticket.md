When a device joins reporting different firmware, the new firmware metadata is kept even if recording the successful update fails, while the in-flight update is left behind; the next join then sees no change and treats it as abandoned. That should be all-or-nothing: if recording the successful update returns an error, keep the old firmware metadata on the device, leave the in-flight update alone, and surface the error through join as it does for other update failures.

Two devices in the same deployment group can also race to start the same firmware delta, and losing that race should not abort the transaction that is adding them. start_firmware_delta should return an error reason of :already_exists when another caller inserted the delta first, and attempt_firmware_delta should treat that as :delta_already_exists instead of failing. Starting over a failed or timed-out delta should still work, including when two callers find the same old delta: exactly one fresh processing delta should be left, it should have a new id, and the successful attempt should return :started.
